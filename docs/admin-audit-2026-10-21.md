# Admin panel audit — 21 October 2026

Scope: login, registration/bootstrap, session lifecycle, all nine console sections, all admin API handlers, shared authorization/data helpers, schema/DDL, and public APIs affected by admin policies. Reviewed local source at commit `22aabd9` with the existing workspace changes. This is an implementation audit, not an authenticated browser or production penetration test. No application code or production data was changed.

Verification: `npm run build` passes. `npm run lint` fails before analysis because the installed dependencies do not contain ESLint. There is no test script in package.json. No local DATABASE_URL or authenticated staff browser session was available for end-to-end checks. Rendered contrast, keyboard behavior, mobile overflow and production infrastructure controls still require verification. No production exploit attempts were made.

Labels: **Defect** = behavior demonstrated by source; **Risk** = failure possible under stated conditions; **Improvement** = recommended capability/design change. P0 = urgent security boundary; P1 = high impact; P2 = normal priority; P3 = polish. Source references are repository-relative with starting line numbers.

## Authentication, registration and access

1. **P0 · Defect · Existing-account registration bypasses password verification.** `src/lib/ccs/admin.js:100–145`: any supplied password of sufficient length is accepted for an existing email; that user is promoted, unbanned and given a session. With admins present this requires the shared invite; without admins it requires no invite. A shared invitation must never prove ownership of another person's account. Require authenticated ownership and recent credential verification, or reject existing emails and promote through an authenticated admin workflow.
2. **P1 · Risk · Public first-admin takeover and bootstrap race.** The first administrator requires no deployment-owner secret. Anyone reaching an uninitialized database can claim it; simultaneous requests can both pass countAdmins. Provision the first admin out of band or require a one-time owner secret and an atomic database guard. Do not reopen bootstrap simply because admin count becomes zero.
3. **P1 · Risk · Shared reusable admin invitation.** `admin.js:91`: no recipient binding, expiry, one-time consumption, or per-invite revocation exists. Replace the global code with expiring, single-use invitations bound to an email and issued by an administrator.
4. **P1 · Risk · No application login/invite throttling.** `src/app/api/auth/login/route.js`, `src/app/api/admin/auth/register/route.js`: no attempt controls are present. Synchronous scrypt also consumes the request's event loop. Add durable account/IP-aware limits and bounded inputs; use asynchronous password hashing. Vercel-side protections were not inspected.
5. **P1 · Improvement · Staff authentication has no MFA or step-up verification.** Administrative deletion, promotion and site publication require only the existing session. Introduce MFA and recent authentication for sensitive actions. Follow [OWASP authentication guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).
6. **P1 · Risk · Staff sessions inherit the public 14-day lifetime.** `src/lib/ccs/store.js:272`: no admin-specific idle timeout, recent-auth timestamp, device inventory or revoke-all control is present in the console. Use an explicit staff session policy and session management UI.
7. **P2 · Defect · Public login succeeds for nonstaff from the admin form.** `AdminLoginForm.jsx:17` uses the general login endpoint, then always navigates to /admin; a student only discovers the restriction on the Forbidden screen. Check staff eligibility in the admin sign-in flow without exposing account existence.
8. **P2 · Defect · Sign-out ignores failure.** `AdminConsole.jsx:153`: non-OK responses and network errors still redirect to login; a valid remaining cookie can redirect straight back to the console. Confirm successful logout and give a retryable error when it fails.
9. **P2 · Defect · Invite availability is reported incorrectly.** `admin.js:79`: inviteRequired is adminCount > 0 regardless of whether CCS_ADMIN_INVITE exists. Registration and onboarding advertise a usable invite path even when the server rejects all invites. Return explicit bootstrap/invite-enabled/disabled states.
10. **P2 · Improvement · Login recovery and password ergonomics.** The admin form lacks a password-reset link, reveal control, explicit autocomplete/name attributes, and a clear session-expiry message. Registration lacks input maximums and the API does not validate email shape or ensure password is a string before using its length.
11. **P2 · Defect · Auth error feedback is not announced.** Login/register error containers lack role=alert or a live region; focus does not move to an error summary. Associate field errors and announce submission outcome.
12. **P2 · Improvement · Public bootstrap diagnostics are unnecessary.** `/api/admin/bootstrap` discloses total user/admin counts and initialization state without authentication. Expose only what the setup screen needs; protect operational counts.

## Authorization and data integrity

13. **P1 · Risk · Moderator profile-edit boundary is much broader than ban/role boundaries.** `admin.js:401,419,437`: moderators can change admin names, handles, profile media, status and badges; ban protects admin targets but profile edits do not. Define a target-role permission matrix and enforce it server-side. Whether moderators should edit other staff is a product decision; current rules are inconsistent.
14. **P1 · Defect · Deleting a user leaves other people's comments on their posts.** `admin.js:526`: deletes comments authored by the user, then their posts, without deleting comments by others on those posts. DDL has no post/comment foreign key. It also does not reconcile commentCount on other posts when removing this user's comments. Delete/recalculate dependent records atomically.
15. **P1 · Defect · Post deletion leaves report references.** `admin.js:588` removes comments and post, but not reports. User deletion likewise leaves report references. Reports can remain actionable with a dead post link. Resolve/preserve reports with a deletion snapshot or delete dependent records by explicit policy.
16. **P1 · Risk · Multi-step destructive changes are not atomic.** User deletion and ban/session revocation use separate statements. Failure midway can leave partial deletion or an unretracted session. Add database transactions or atomic database operations supported by the driver, with failure-injection checks.
17. **P1 · Risk · Whole-document settings saves lose concurrent changes.** `admin.js:286`: reads a JSON object, merges and replaces it. Two saves can each read old state and overwrite each other's unrelated edits. The UI permits overlap even while saving. Use atomic field updates or versioned compare-and-swap, and serialize local writes.
18. **P2 · Risk · Whole-profile saves also lose concurrent changes.** Badge, status and profile helpers independently read/replace profile JSON; concurrent staff/user edits can revert each other. Add version checks or targeted atomic updates.
19. **P2 · Risk · Last-admin checks are race-prone and count banned admins.** `admin.js:379,526`: checks and updates are separate; countAdmins includes accounts that cannot sign in. Self-demotion UI is always disabled even when the server would permit it. Enforce an atomic minimum of usable admins and make UI rules match.
20. **P2 · Defect · Several post operations report success for nonexistent IDs.** Pin/edit/delete do not check affected rows. Empty PATCH also succeeds. Return 404 or a clear validation error, and avoid auditing nonexistent changes as successes.
21. **P2 · Defect · Post-body rules differ between staff and public editing.** `admin.js:580` accepts empty bodies and silently slices at 16,000; public creation uses 12,800 and rejects excess. Centralize policy, validate before writing and return canonical saved content to the client.
22. **P2 · Defect · JSON shape validation is inconsistent.** Most handlers parse JSON but do not reject null, arrays or scalar roots. Some field accesses then throw; settings accepts arbitrary keys and unvalidated policy values. Add per-operation schemas, explicit types, allowed fields and payload limits.
23. **P2 · Risk · Session revocation is the public ban boundary.** `store.js:192` does not reject banned users when resolving a session; staff requireStaff does. A ban depends on successful deletion of every session, including concurrent sign-ins. Check banned state during all session resolution and make ban/revocation atomic.

## Shared console behavior and accessibility

24. **P2 · Defect · Navigation has no URL state.** `AdminConsole.jsx:90`: refresh resets to Overview, browser history cannot traverse panes, and staff cannot bookmark/share a filtered view. Use routes or URL search parameters for sections, filters and selected records.
25. **P2 · Defect · Drafts disappear on navigation.** Conditional panes unmount; post-editor backdrop/Cancel closes immediately; landing Reload/defaults overwrite the editor. Add dirty-state tracking, explicit discard confirmation and appropriate draft persistence.
26. **P2 · Defect · Saving patterns contradict each other.** Status and lists save on blur, switches save immediately, profiles/tickets use Save, CMS uses Publish. Most lack durable success feedback. Standardize explicit Save/Cancel for related edits and explain any autosave state.
27. **P2 · Risk · Most mutations allow repeated submissions.** Publish announcement, ticket save, role changes, profile save and destructive row actions have no pending lock. Duplicate announcements and out-of-order updates are possible. Add per-operation pending state and idempotency where creation is retryable.
28. **P2 · Risk · Search responses can arrive out of order.** Users/Posts debounce request starts but do not abort or sequence requests. An old response can replace a newer filter result. Add AbortController or sequence guards.
29. **P2 · Defect · Failure is often displayed as empty or endless loading.** Announcements/reports/tickets initialize to []; failed loads can leave a false empty message. Overview's first failed request records pollError but returns Skeleton before displaying it. Site settings can also remain a skeleton after failure. Model loading, error, empty and success separately, with Retry.
30. **P2 · Defect · Error handling is inconsistent across APIs.** ensureReady and many database calls sit outside error handling; unexpected errors produce generic/non-JSON failures. A rejected initialization promise is retained by drizzle-client, preventing recovery in that process. Return safe structured errors, log server detail, and reset failed initialization state for retry.
31. **P2 · Defect · Many inputs have no accessible label.** Search/filter controls, profile fields, ticket reply and CMS textarea rely on placeholders or adjacent divs. SettingRow is an unnamed button with no switch role or checked state. Add label associations, role=switch/aria-checked and accessible names.
32. **P2 · Defect · Text-input focus indication is removed.** adminUi.input and AdminConsole.inp set outline:none without replacement. Add a visible keyboard-focus style. Native select has a separate CSS focus treatment; verify its contrast independently.
33. **P2 · Defect · Closed mobile drawer stays in the keyboard/accessibility tree.** It is translated off screen rather than made hidden/inert. Open drawer has no focus containment/restoration. Use a properly managed dialog/drawer and prevent focus reaching background controls.
34. **P2 · Defect · Post modal lacks focus management.** role=dialog is present, but no focus trap, initial focus, return-focus behavior or Escape handler. Its close glyph lacks a descriptive accessible label. Implement a shared accessible dialog.
35. **P2 · Risk · Fixed input widths can exceed narrow containers.** inp(520/560/620), dense profile rows and nonwrapping CMS header controls create likely small-screen overflow; parent overflowX:auto masks rather than adapts it. Use width:100%, max-width, wrapping groups and a compact record editor. Verify 320/375/768/920px and 200% zoom.
36. **P3 · Improvement · Visual and language consistency.** Mixed emoji navigation, diagnostic blue/purple scrollbars, rose admin chrome, raw action identifiers, variable capitalization, 10–13px labels and technical database/env copy compete with operational tasks. Use a shared icon set, readable type scale, plain labels and consistent spacing; move deployment details to diagnostics. Measure rendered contrast before claiming compliance.

## Each operational section

37. **P2 · Defect · Landing link is offered to moderators but API is admin-only.** All sections are rendered for all staff. Hide unavailable actions or show a deliberate access explanation; also hide admin-onboarding instructions from moderators who cannot promote users.
38. **P2 · Defect · Moderator Ban buttons are shown for admins.** Server correctly rejects those bans, but the UI invites a failed action. Render capability-aware controls from the same permission policy.
39. **P2 · Improvement · Users list needs a usable record workflow.** Search covers only ID/email although names/handles dominate the interface. No pagination, banned-state filter or date sorting exists. Large profile forms repeat for every user. Add name/handle search, pagination and a dedicated detail editor with last activity and action history.
40. **P2 · Defect · Profile editors can show stale values.** Status uses defaultValue; StaffForumProfileFold resets only when user.id changes. Server-normalized/external updates can leave old drafts or fields visible. Track baseline, dirty state and server version explicitly. Empty status behaves differently through the status and profile endpoints.
41. **P2 · Improvement · Posts screen omits moderation context.** Lists raw truncated Markdown, author IDs and counts; imageUrl is returned but not shown. No convenient full-post context/comment moderation exists in this pane. Add author identity, image/full preview, post link and focused comment actions; preserve original content/reason when staff edits a user's words.
42. **P2 · Improvement · Reports lack a complete review workflow.** Only newest 80 open reports are returned, without pagination/history or a visible truncation warning. Resolve only closes the report; there is no linked moderation action, reason, assignment or content snapshot. Add contextual review, explicit outcome, resolution note and history. Use an atomic status=open update to prevent simultaneous contradictory resolutions.
43. **P2 · Improvement · Announcements cannot be edited or repinned.** API/UI offer create/delete only. Fixing a typo requires deletion and republication. Add edit/pin workflows, length counters matching server rules, preview and explicit publication feedback.
44. **P2 · Improvement · Tickets use one overwriteable reply.** No conversation history, responder identity, assignment, priority or in-progress status is modeled. A later reply replaces the previous reply, and reloading after one save can reset another ticket's unsaved draft when its props change. Start with append-only replies, per-ticket drafts, pending state and visible author/time.
45. **P1 · Defect · Several policy controls do not enforce policy.** guestReadOnly is not consulted by the public feed API; bannedWords has no posting enforcement. requireEmailVerification and autoModLinkPosts are explicitly marked mock but remain interactive. registrationOpen is enforced. Implement the missing policies across relevant public read/write routes or remove/disable those controls until real; never imply a security policy is active when it is only stored.
46. **P2 · Defect · Landing CMS accepts invalid semantic values.** Valid JSON alone passes; mergeLandingCms allows wrong scalar/element types and silently restores defaults for empty arrays. A staff typo can break public rendering, and intentional empty sections cannot consistently stay empty. Use a strict schema and a form/preview, distinguish empty from missing, and reject invalid payloads before publishing.
47. **P2 · Improvement · Landing publication has no revision protection or rollback.** Raw JSON is the only editor, Reload/defaults can discard changes, and a publish replaces the live root with no version check, draft or history. Add a typed editor, draft preview, change summary, revisions and restore. 'Invalid JSON' currently uses the green success-message styling; reset copy says Save although the button says Publish.
48. **P2 · Defect · Audit trail is incomplete and silently lossy.** appendAudit catches every failure; logins/failures/logout are not recorded here. Edits mostly record keys/length rather than before/after/reason. Retain required security events and attributable changes, alert on audit-write failures, and define whether sensitive changes must fail if their audit record cannot be stored.
49. **P2 · Improvement · Audit UI stops at 200 entries.** No pagination, actor/action/date filters, export, linked identity or refresh is offered. It displays raw IDs/action keys/JSON. Add searchable, readable event history with retention rules and controlled export; avoid unnecessarily persisting email addresses in deletion metadata.
50. **P2 · Defect · Overview diagnostics are expensive and partly mislabeled.** Every 14 seconds getOverview fetches full user records (including credential/profile fields it does not need), all post/comment IDs, and multiple storage scans. SQL LENGTH(text) counts characters but the UI formats the result as bytes. Use COUNT/conditional aggregates, appropriate octet_length or explicitly labeled character totals, and cached diagnostics with a slower refresh.
51. **P2 · Improvement · Serverless diagnostics are not deployment health.** PID, uptime and memory refer to the worker serving that request; next request may reach another worker. Client history lasts only the current pane/session. Label this clearly, pause polling in hidden tabs, avoid overlapping requests and use durable telemetry for historical operational claims. Put open tickets/reports and pending actions ahead of runtime trivia.
52. **P2 · Risk · Unbounded lists and mixed schema ownership.** Users/posts/tickets/announcements load all matching rows. Drizzle schema omits foreign keys that bootstrap DDL creates, while other important relationships lack either. Runtime cold starts run DDL before authorization. Add bounded cursor pagination, reconcile schema definitions/migrations and move schema changes to a controlled deployment step.

## What is already sound

Admin API routes generally perform server-side staff checks; role changes, announcement writes and site writes have admin-only checks. Sessions use random tokens with HttpOnly/SameSite cookies and Secure in production. Password verification uses salted scrypt and timing-safe comparison. API mutations have an origin check, and global security headers exist. These are useful foundations, but they do not neutralize the registration bypass or incomplete policy enforcement.

## Recommended implementation order

1. Close registration ownership/bootstrap/invitation gaps; add rate limits and regression coverage for anonymous/student/moderator/admin/banned users.
2. Define/enforce the role-target permission matrix; repair policy enforcement and deletion integrity; make important changes atomic.
3. Standardize API validation/error contracts, concurrency/versioning, pending/success/error states and audit guarantees.
4. Rework the console navigation, record editors, accessible controls/dialogs and responsive behavior.
5. Complete reports/tickets/announcements/CMS workflows and replace heavy overview polling with useful operational summaries.

Before marking the sweep complete at runtime: restore/install missing dev dependencies; run lint and focused regression tests against a disposable database; exercise every operation with each role; test keyboard-only, screen-reader labels, mobile widths and zoom; verify production cookie/proxy behavior and any infrastructure rate limits. None of those unperformed checks is represented as passed here.
